# EcoBite Customer App

React Native + Expo (SDK 57) + Expo Router + TypeScript. EcoBite is a **surplus-food marketplace**: customers discover discounted food bags from restaurants, pay, and **pick the order up in person**.

Status: **U0, U1.1 … U1.7 done** (architecture, shared UI, auth/onboarding, discovery, Food Bag → Cart, Checkout → Payment, the pickup flow, and Orders → Order Detail / Status, Account → Edit Profile → Logout). Only the AI screens (`/ai`, `/ai/history`) are still placeholders; U1.8 has NOT started.

Read before large changes: `docs/ARCHITECTURE.md`, `docs/MVP.md`, `docs/AI-FLOW.md`, `docs/SCREEN-MAPPING.md` (screen ↔ route ↔ feature ↔ decisions D-1…D-17, all APPROVED).

## Product rules (non-negotiable)

- **Self-pickup only.** There is NO delivery: no couriers, no delivery address, **no delivery-fee row** (D-13), no driver tracking. Never reintroduce delivery unless the user explicitly asks. The reference's "Phí giao hàng" rows are intentionally NOT built.
- Customer flow: discover → restaurant → food bag → cart → checkout → payment → **Pickup QR** → go to restaurant → staff verifies QR → receive food → completed.
- **Payment QR ≠ Pickup QR.** Payment QR: shown by the app, scanned by the customer's banking app (`PaymentQr`, `services/payment`). Pickup QR: shown by the customer, scanned by restaurant staff (`PickupQr`, issued only after payment). It holds an **opaque `token`** (what the QR encodes) **and the human `orderCode`** shown below the QR for manual entry (D-7). Never mix the types, names or screens.
- **Multi-restaurant cart (D-1).** One `Cart` may hold bags from several restaurants. Checkout groups items by restaurant and creates **one `Order` per restaurant**, each with its own `orderCode`, payment session and pickup QR (orders of one checkout share `checkoutId`).
- **Order lifecycle (D-2).** Main sequence, strictly linear (`types/order.ts`, `constants/order-status.ts`, `utils/order-lifecycle.ts`): `placed` → `paid` → `preparing` → `ready` → `qr_verified` → `picked_up` (= the reference's COMPLETED). **`cancelled` and `expired` are terminal exception states OUTSIDE the sequence** (`OrderExceptionStatus`); `Order.status` is `OrderState = OrderStatus | OrderExceptionStatus`. Cancel only while `placed`/`paid`; expire only from `placed`. Payment outcome is tracked separately in `paymentStatus`; a failed payment leaves the order `placed` for a 5-minute retry.
- Order money (`OrderMoney`): `total = subtotal - promoDiscount - ownBoxDiscount`. No delivery fee, ever.
- **Payment (D-4, D-6, D-10).** Payment method screen (6.8) exists; **QR bank transfer is the only enabled method**, the others are shown disabled with "Sắp có". The Payment QR and all its states (qr → waiting → success/failed/expired) live in **one route with phases**: `/order/[orderId]/payment` (`PaymentPhase`, `features/payment`). Hold = 10 min, retry after failure = 5 min.
- After Payment Success go to **Pickup QR (8.3)** directly (D-3); do not insert 8.1 before it.
- **Order routes (D-5):** `/order/[orderId]` = completed order detail (9.5); `/order/[orderId]/status` = active order status timeline (8.2).
- **Auth flow (U1.2):** Splash → Onboarding → Welcome → Register → OTP → Create Profile → Location Permission → Select Location → Home; Login → (Create Profile | Location Permission | Home) depending on the account. State machine: `features/auth/auth-state.ts` (pure reducer), session store `auth-store.ts` (module singleton, no persistence, resets on reload), routing `auth-routing.ts` (`resolveAuthRoute`, `canAccessAuthScreen`), orchestration `auth-actions.ts`, mock backend `services/auth`. Screens only call `auth-actions` and navigate to the returned route; every auth screen calls `useAuthGuard`. **Demo values (mock only, no SMS, no backend): OTP `1234` for every phone; demo account `duong.nguyen@email.com` / `0912 345 678`, password `EcoBite123`** (`data/mock/auth.ts`). Location Permission is a mock screen: never use expo-location/GPS/maps. Select Location offers exactly Cầu Giấy, Đống Đa, Ba Đình, Thanh Xuân and stores the choice in the auth session (`useAuth().area`); Home/discovery reads it from there.
- **Discovery (U1.3):** Home (`(main)/home`) → Search (`/search`) → Results (`/search/results?q=`) → Restaurant Detail (`/restaurant/[id]`) → Food Bag (placeholder until U1.4). Logic lives in `features/discovery` (`useCatalog`, `useHome`, `useSearch`, `getHomeView`, session-level recent searches) and `features/restaurant` (`useRestaurant`, `getPrimaryBag`); pure rules in `utils/restaurant-listing` (`buildRestaurantListings`, `filterByCategory`, `sortByArea`, `findListing`) and `utils/search` (`searchListings`, accent-insensitive, every word must match name / category / bag name+summary). Home lists **all six** demo restaurants (`res_01`…`res_06`) and puts the selected area's (`useAuth().area`) first; each restaurant has an `areaId` and a Hà Nội address. Home and cards show the restaurant's **first available bag** (`featuredBag`), as the reference does. **No GPS, maps or distance maths** (`distanceKm` is a mock number). The AI orb is mounted on Home only.
- **Cart (U1.4):** the session cart store lives in `features/cart` (`cart-store.ts` module singleton, no persistence, resets on reload; `cart-reducer.ts` pure; `cart-actions.ts` = `addBagToCart`, `setCartItemQuantity`, `removeCartItem`, `clearCart`, `setRestaurantPickupSlot`; `cart-view.ts` builds the display model; `useCart`, `useCartCount`, `useCartView`). Rules stay in `cart-logic` and money in `utils/order-pricing` (`groupCartByRestaurant`, `computeOrderMoney`): the store/reducer/screens never compute prices. **Cart count = number of food-bag UNITS across all restaurants** (2 + 1 bags = 3): it is the tab badge and the "N túi" in the summary; restaurants are not counted. Adding is validated by `tryAddToCart`: quantity ≤ `bag.left` minus what the cart already holds, sold-out bags and invalid ids are rejected (`not_found | sold_out | limit_reached | invalid_quantity`). The cart is multi-restaurant (D-1): the Cart screen renders one section per restaurant, each becomes one Order at checkout; the pickup slot is kept per restaurant (`Cart.pickupSlots`) but chosen at checkout (U1.5), so Cart shows "Chưa chọn giờ" until then. Food Bag Detail (`/food-bag/[id]`, also the sold-out state 5.7) opens the Add-to-Cart sheet (`/food-bag/[id]/add-to-cart`, `transparentModal`) which adds to the store and then `router.dismissTo('/cart')`. The Cart button "Tiếp tục" opens Checkout (U1.5).
- **Checkout & payment (U1.5), decisions D-18 … D-20 in `docs/DECISIONS.md`:** Cart → `/order/checkout` → `/order/pickup-time?restaurantId=` (per restaurant) → `/order/summary` → `/order/payment-method` → `/order/[orderId]/payment` → `/order/[orderId]/payment-success` → `/order/[orderId]/pickup-qr` (placeholder until U1.6). The order of Summary and Payment Method follows the U1.5 brief, not the D-4 mapping table (D-19). Logic lives in `features/checkout`: `buildCheckoutView` (money via `priceCartGroups` / `sumOrderMoney` in `utils/order-pricing`), `selectPickupSlot` (slot per restaurant, stored in the cart store; only slots with capacity inside the bags' pickup-window intersection), `placeCheckout` (validates, `api.checkout` = ONE Order per restaurant, **clears the cart once the orders are committed**, creates the first payment session), `ensurePaymentSession` (one current session per order, lazily), `retryOrderPayment` (new session, same order, never a new order), `getCheckoutProgress`. **Multi-restaurant payment is sequential (D-18):** one Payment QR / 10-minute hold per order; after a success the screen offers "Thanh toán đơn tiếp theo" while a sibling order is still `placed`; when none is left it goes straight to Pickup QR of the first paid order (D-3). The payment route is ONE screen with phases qr → waiting → success | failed | expired (D-6) driven by `usePaymentStatus`; failed = order stays `placed` + retry within 5 minutes, expired = order `expired` (terminal). Payment QR (`PaymentQrCard`, `PaymentQr`) is never a pickup QR. QR bank transfer is the only enabled method. No promo UI yet (model and pricing work).
- **Pickup flow (U1.6), decisions D-21 / D-22 in `docs/DECISIONS.md`:** routes `/order/[orderId]/pickup-qr` (8.3) → `pickup-instructions` (8.1) → `ready` (8.4, also the preparing state) → `arrived` (8.5) → back to `pickup-qr` for the staff scan → `verified` (8.6) → `completed` (8.7); `status` is the 8.2 timeline. Logic in `features/pickup`: `getPickupStage` / `getPickupGate` / `resolvePickupRoute` (pure, derived from the existing lifecycle — NO new state), `usePickupScreen` (polls the order every 1.5 s, gates unpaid / expired / cancelled / missing-QR orders, redirects a screen opened at the wrong stage), `simulateStaffScan` (mocked scan = `api.verifyPickupQr`, ready → qr_verified) and `confirmReceived` (qr_verified → picked_up). **The lifecycle stays linear: ready → qr_verified (staff scan, "QR đã được xác nhận") → picked_up (customer taps "Tôi đã nhận đủ túi", "Đã nhận hàng").** "Tôi đã tới quán" only opens the QR. The customer app never scans (no camera); the restaurant / staff steps are the DevMenu "Advance" control (D-17). `verifyPickupQr` rejects wrong token / payment QR payload / other order's token ("Invalid pickup QR"), a not-ready order, and an already used QR. Multi-order pickup is sequential (D-21): each order has its own QR and state, Order Completed offers the next order (`getNextPickupStep`).
- **Orders, Account, logout (U1.7), decisions D-23 / D-24 in `docs/DECISIONS.md`:** `(main)/orders` has the reference segments Đang xử lý / Đã xong / Đã huỷ (`features/order-history`: `getOrderTab`, `filterOrders`, `countOrdersByTab`, pure and read-only). **`resolveOrderRoute` is the one place that decides where an order opens (D-5):** placed → payment, paid / preparing / ready → `/order/[orderId]/status`, qr_verified → QR Verified, picked_up / cancelled / expired → `/order/[orderId]` (read-only detail; it redirects a live order to its flow). Orders belong to accounts: `api.checkout({ cart, userId })`, `api.listOrders({ userId })`; another account's order is "not found". **The whole app is behind one root guard** (`useAuthGate` → `getProtectedRedirect`, only splash and `(auth)` are public) that reuses the U1.2 auth stages. Account (`(main)/account`) shows the session profile and impact derived from the account's completed orders (`utils/impact`); Edit Profile (`/account/edit`) saves name and default area (`features/account/updateProfile`; phone and email read-only). **Logout (`signOut`) clears the auth session, the cart and the checkout / payment sessions and goes to the auth entry; orders are kept.** Reorder ("Đặt lại túi này") adds the same bags to the current cart through the normal add-to-cart rules. Unsupported reference screens (saved, wallet, promo, notifications, settings, help, legal, impact detail, invoice, review, cancel) are NOT built.
- **Auth routing (D-8, D-9):** first successful login → Location Permission → Select Location → Home; returning authenticated user → Home (`features/auth/auth-routing.ts`). **Guest preview is NOT supported**; the "Xem trước không cần tài khoản" button stays hidden.
- **Bottom tabs (D-14): Home · Orders · Cart · Account.** Search is NOT a tab; it is a stack flow `/search` (3.4) → `/search/results` (3.5).
- **Light theme only (D-11).** No dark palette, no `useColorScheme`.
- Follow the approved 24-screen MVP flow in `docs/MVP.md`. Do not invent screens outside the approved product flow.

## Scope rules

- **No real payment integration** (PayOS, Casso, SePay, …) unless explicitly requested. Payment is simulated in `services/payment`.
- **No real AI integration** unless explicitly requested. AI is UI + mock responses only.
- No real backend; `services/api` is mock-backed behind an interface.
- **Dependencies (D-15):** approved and installed: `react-native-svg`, `expo-linear-gradient`, `react-native-qrcode-svg`. Everything else stays uninstalled until approved (`expo-clipboard`, `expo-image-picker`, `expo-brightness`, `expo-location`, `@expo/vector-icons`, …). Explain why before adding any dependency.

## Architecture rules

- TypeScript strict. Path alias `@/*` → `src/*`.
- Routes live in `src/app` and stay thin: they compose components and call feature hooks. **No business logic in UI components or route files.** Logic goes in `features/*`, `utils/`, or `services/`.
- Data access goes through `services/*` interfaces (`api`, `payment`, `ai`). Never import from `data/` in components/screens.
- **Mock data lives in `src/data/`** only, shaped like the reference `js/mock-data.js` (six restaurants `res_01`…`res_06` with Hà Nội addresses in the four areas, `bag_01`, `bag_01`, `EB-2409-017`…). Never hardcode mock arrays in screens.
- **Pure business rules** (lifecycle, pricing, grouping, order codes) live in `utils/` and `features/cart`; services call them, UI never re-implements them.
- **AI is a separate module** (`app/ai`, `features/ai`, `components/ai`, `services/ai`, `data/ai`, `types/ai`). It must not import core ordering features; it references core entities by id only. Core code must not depend on AI internals, except mounting the orb through its public export.
- **Design tokens (D-12):** `src/constants` values come from the **82-screen HTML reference** (`css/styles.css`) and are verified against it by `npm run verify`. Font: **Nunito only** (600/700/800). Never Be Vietnam Pro. No hardcoded hex colours or magic spacing in components. Design for 390×844.
- **Feature folders (D-16):** `auth location restaurant food-bag cart payment pickup order-history ai` plus `discovery notifications account`. Checkout/promo/summary logic stays inside `cart`; reviews stay inside `order-history`. `features/dev` is dev tooling (below).
- **Dev-only controls (D-17):** `components/dev/DevMenu` is mounted in `app/_layout.tsx` only when `__DEV__`. It calls `features/dev/dev-actions`, which dispatch to **existing mock services** (`api.markOrderPaid`, `simulateRestaurantProgress`, `verifyPickupQr`, …). Never duplicate business logic there, never build the old HTML demo panel, never import dev tooling from production code.
- **Shared UI (U1.1):** build screens from `components/common`, `restaurant`, `food-bag`, `cart`, `order` instead of ad-hoc styles. Shared components are presentational: no services/features/data/router imports, no hard-coded colours/font names/weights (use `src/constants`). Icons: `Icon` from `components/common/icons` (reference paths). Use `PaymentQrCard` for the Payment QR and `PickupQrCard` for the Pickup QR (never swap). `OrderPriceBreakdown`/`CartSummary` have no delivery row. Tabs come from `constants/tabs.ts` via `BottomTabBar`. `AiOrb` has no AI logic; its caller decides where it is mounted and where it navigates.
- Do not arbitrarily change the architecture. **Before any major architectural change, explain the reason to the user and get agreement.**

## Commands

- `npx expo start` (`npm run web` / `android` / `ios`) — run the app
- `npx tsc --noEmit` — typecheck (run after changes; typed routes are generated by Expo)
- `npm run verify` — foundation checks: routes/links, tabs, tokens vs reference CSS, cart/checkout, payment, order lifecycle, pickup QR, dev controls, AI. Run after touching routes, tokens, types or services
- `npx expo export --platform web` — production bundle smoke test
